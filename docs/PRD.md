# Product Requirement Document (PRD): SmartWater Guardian

## 1. エグゼクティブサマリー
* **プロダクト名**: SmartWater Guardian（スマートウォーター・ガーディアン）
* **コンセプト**: 「消火栓貼付型IoT音響センサー」×「ハイブリッドAI解析」による持続可能な次世代インフラ漏水監視＆自動アセットマネジメントプラットフォーム
* **コアターゲット**: 全国の自治体・水道事業体、防災インフラ管理者
* **開発目的**: 老朽化水道管の破裂事故・道路陥没を**微小漏水（Level 1）の段階**で防ぎ、経営難の水道事業体における漏水調査コストを削減する。

## 2. 漏水深刻度モデル＆判定ロジック

深刻度は **Level 0〜3 の4段階**で表現する。Level 0（正常）を独立して持つことで、「異常なし」と「AIだけが検知できる微小漏水」を画面上・API上で明確に区別する。

* **Level 0：正常（異常なし）**
  * 状況: 環境ノイズのみ。漏水帯域に卓越ピークなし。
  * AIの役割: ベースラインとして記録し、Level 1 との対比を成立させる。
  * 表示: グレー（`#64748b`）／`status="normal"`

* **Level 1：微小漏水（ピンホール・継手部ゆるみ）** 【★メインターゲット／唯一の差別化領域】
  * 状況: 地中でポタポタ漏水。**水圧変化なし・地上は無音**で、人間は目視・聴覚では検知不能。既存の水圧監視・巡回点検では発見できない。
  * AIの役割: FFT周波数解析（500Hz〜1500Hz）で早期検知し、道路陥没を予防する。
  * **本プロダクトが「AIでなければ成立しない」と言えるのは、この Level 1 の検知に限られる**。Level 2/3 は水圧計や住民通報でも捕捉されうるため、価値訴求・デモの主役は必ず Level 1 に置く。
  * 表示: 黄緑（`#84cc16`）／`status="watch"`

* **Level 2：進行性漏水（ひび割れ拡大）**
  * 状況: 噴出・土砂削り開始（陥没前兆）。
  * AIの役割: 異常音増幅をアラート化し、優先補修起票。
  * 表示: 黄（`#f59e0b`）／`status="warning"`

* **Level 3：管路破裂・大漏水**
  * 状況: 水圧急低下、断水・赤水発生。
  * AIの役割: 被災時等に即座に破裂エリアをマッピングし優先閉栓バルブ指示。
  * 表示: 赤（`#ef4444`）／`status="critical"`

## 3. システムアーキテクチャ＆データフロー
1. **IoT Edge**: 消火栓裏の磁石型センサーが深夜帯に音波・GPSデータを取得（2万円モデル）。
2. **Backend API (FastAPI)**: 疑似センサーからの生音データ（PCM16 / Base64）およびメタ情報を受信。
3. **AI Pipeline (Python / FFT)**:
   * ノイズカット（100Hz以下除去）およびFFT周波数スペクトル解析。
   * 漏水確信度（0〜100%）および深刻度（Level 0〜3）の判定。
4. **LLM Agent (OrcaRouter経由)**:
   * 位置情報から自治体配管台帳（GIS）を参照。
   * 適合補修パーツ（例：鋳鉄管150mm用クランプ）および概算見積もりを自動選定し、Teams/Emailへ現場作業指示書を自動起票。
5. **Frontend (Next.js / GIS Dashboard)**: リアルタイム漏水マップ表示、アラート点滅、波形グラフ可視化。

### 3.1 収益モデル（誰が・誰に・いくら払うか）

| 項目 | 内容 |
|---|---|
| **売り手** | 本プロダクト提供事業者（SaaS） |
| **買い手** | 水道事業体（市町村の水道局・企業団）。**予算執行者は水道事業会計**であり一般会計ではない |
| **課金構造** | ① センサー初期費（ハードウェア実費＋設置）② 月額SaaS利用料（センサー台数課金）③ オプション：LLM自動起票の従量課金 |
| **導入経路** | 実証事業（数十台規模・単年度）→ 効果検証 → 本格導入（数百〜数千台・複数年契約） |
| **買い手のROI源泉** | 現行の漏水調査委託費の削減、破裂事故に伴う道路復旧・断水対応の回避、無収水量（有収率改善）の低減 |

> 具体的な単価・台数別の年間契約額・ROI試算・KPI「推定削減コスト」の算定式は **`docs/business-model.md`** に定義する。ダッシュボードの推定削減コストは必ず同ファイルの算定式を参照して算出し、ハードコードしない。

## 4. 機能要件 (Functional Requirements)
* **FR-1**: 音データ（PCM16）の自動周波数解析・漏水判定機能（Level 0〜3）
* **FR-2**: GISマップ上への漏水リスクノードのリアルタイム描画機能
* **FR-3**: 音波形×配管台帳の2段階照合による補修パーツ自動選定機能
* **FR-4**: 自律型LLMエージェントによる自動起票・通知機能（Teams/Email）
* **FR-5**: 防災モード（震災時の一括被害エリアマッピング機能）
  * ※ **デモスコープ外（P2余力枠）。** P0/P1が全て完了した場合のみ着手する意図的なスコープ判断であり、未実装を前提とする。
* **FR-6**: **LLM原価の計測・可視化機能**
  * 起票1件あたりの入力／出力トークン数と円換算原価を記録し、起票結果の画面上に表示する。
  * 生成元（`llm` / `fallback`）を併記する。詳細は `docs/llm-cost.md`。

## 5. 非機能要件 (Non-Functional Requirements)
* **NFR-1**: 判定処理レイテンシ 3秒以内（2秒/16kHz の音声1件あたり）
* **NFR-2**: 屋外環境ノイズ下における検知堅牢性（正規化処理・Data Augmentation適用）
* **NFR-3**: 5日間のハッカソン期間内で動作可能なMVP実装
* **NFR-4**: **シークレット管理**
  * APIキー等の機密情報は**サーバー側の環境変数でのみ**保持する。
  * 次のいずれにも出現させない: リポジトリ（`.env` の追跡およびgit履歴）／`NEXT_PUBLIC_*` を含むクライアントバンドル／ログ出力／APIレスポンス／例外メッセージ。
  * 万一コミットされた場合、追跡解除では無効化されない。**キーのローテーション（旧キー失効＋再発行）を最優先で行い**、その後に履歴から除去する。
* **NFR-5**: **LLM障害時の継続性**
  * 外部LLM APIの障害・レート制限・キー失効時も、規定ルールによる代替結果を返して画面を破綻させない。
  * 生成元（`llm` / `fallback`）を UI に明示し、**障害時でも生成元について嘘をつかない**。
  * 環境変数によりフォールバックを強制でき、オフラインでのデモリハーサルが可能であること。

## 6. 評価軸
1. **デモ完成度:** 触れて30秒で異常検知〜自動見積起票の価値が伝わるUI/UX。
2. **課題の実在性:** 水道局の現場取材・統計等（熟練者不足・漏水調査コスト）の一次情報に基づく課題解決。→ §1.1 の出典ステータス表で管理。
3. **ビジネス成立性:** 自治体/水道事業者向けのSaaS/B2Gモデル（導入・月額・削減コスト比較の可視化）。→ §3.1 および `docs/business-model.md`。
4. **LLMコスト:** 1起票あたりの実測原価算出、Prompt圧縮・プロキシキャッシュによる削減策の提示。→ FR-6 および `docs/llm-cost.md`。
5. **AI必然性:** 音響波形解析×Orcarouter API（LLM部材自動選定）による完全自動化。→ **Level 1（人間には検知不能な微小漏水）を主役に据えることで訴求する**（§2）。
6. **技術作りこみ:** FFT解析、FastAPI/Next.js構成、TDD（カバレッジ80%以上）。
7. **セキュリティ:** インフラ位置情報・APIキーの厳格保護（環境変数・プロキシ経由）。→ NFR-4。
8. **次世代性:** 1年前には不可能だった「検知から修繕手配までの即時自動化」。

### 6.1 デモシナリオの訴求方針

デモの山場は **Level 3 の大漏水ではなく Level 1 の微小漏水**に置く。Level 3（水圧急低下・断水）は既存の水圧監視や住民通報でも捕捉可能であり、それを主役にすると「AIでなければできない」という訴求が成立しないため。

> **訴求文:** 「異常を検知した」ではなく、**「人間には無音・水圧変化もない段階で、AIだけが漏水に気づいた」**

デモは Level 0（正常）との対比から入り、Level 1 検知 → 500〜1500Hz のスペクトルピークによる判定根拠の提示 → LLMによる補修部材・概算見積・作業指示書の自動起票（実測API原価つき）へ繋げる。詳細なタイムラインは `docs/ui-wireframe.md` を参照。
