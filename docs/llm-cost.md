## 1. 何を1件と数えるか

**課金単位＝「1起票」**（`POST /api/v1/alerts/{telemetry_id}/work-order` の1回の成功呼び出し）。

1起票で発生するLLM呼び出しは **1回**。マルチターンにしない。理由は次の2点。

- 部材選定・見積・作業手順・通知文面を**1回の構造化JSON出力**で得る設計（OR-2）のため、往復のたびにプロンプト全体を再送するコストが発生しない。
- 往復回数が増えるほど原価の分散が大きくなり、「1起票あたり◯円」と言い切れなくなる。

## 2. 計測設計（BE-5 実装時に必ず入れる）

### 2.1 記録するフィールド

`WorkOrder` スキーマ（`app/schemas/work_order.py`）に以下を追加する。

| フィールド | 型 | 内容 |
|---|---|---|
| `prompt_tokens` | `int` | 入力トークン数（APIレスポンスの usage から取得） |
| `completion_tokens` | `int` | 出力トークン数（同上） |
| `cost_yen` | `float` | 円換算原価（§2.2 の式で算出） |
| `source` | `Literal["llm", "fallback"]` | 生成元。`fallback` 時は `cost_yen = 0.0` |
| `model` | `str` | 実際に使われたモデル識別子（Orcarouterはルーティングするため必須） |
| `latency_ms` | `int` | 呼び出しのレイテンシ |

> **重要:** `source="fallback"` の場合は LLM を呼んでいないため原価は 0。`cost_yen` を推定値で埋めない（**実測でないものを実測として見せない**）。

### 2.2 円換算の式

```
cost_yen = (prompt_tokens     / 1000 × unit_price_input_per_1k)
         + (completion_tokens / 1000 × unit_price_output_per_1k)
         × usd_jpy_rate
```

| 定数 | 値 | ステータス |
|---|---|---|
| `unit_price_input_per_1k` | — | **要設定** — 実際にルーティングされるモデルの単価を Orcarouter のダッシュボード/ドキュメントで確認する |
| `unit_price_output_per_1k` | — | **要設定** — 同上 |
| `usd_jpy_rate` | — | **要設定** — 為替は固定値で持ち、値と取得日をここに記録する |

> Orcarouter はリクエストを複数モデルへルーティングするため、**呼び出しごとに単価が変わりうる**。レスポンスに実際のモデル名と usage が含まれる場合はそれを優先し、含まれない場合は事前に指定したモデルの単価で計算したうえで「概算」と明記する。

### 2.3 出力先

1. **構造化ログ**: 起票のたびに1行 JSON で記録（`telemetry_id` / `model` / トークン数 / `cost_yen` / `source` / `latency_ms`）。
2. **画面**: FE-6 の起票モーダル脚注に「本起票のAPI原価: ¥X.XX（モデル: ◯◯）」を表示。
   → **審査員に実測原価を画面上で見せられる**ことが、評価軸4における最大の差別化になる。
3. **本ドキュメント §3**: デモリハーサル時の実測値を転記する。

### 3.1 事前見積（実測前の目安）

実測前にオーダー感を持っておくための**概算**。実測値で必ず置き換える。

| 構成要素 | 推定トークン数 | 内訳 |
|---|---|---|
| システムプロンプト | 200〜300 | 「日本の水道事業体の補修設計担当者」の役割定義＋出力制約 |
| `WorkOrder.model_json_schema()` | 600〜900 | **最大の入力要素**。§4-1 の削減余地が最も大きい箇所 |
| 解析結果（AnalysisResult） | 80〜120 | `spectrum` の128点は**送らない**（§4-2） |
| 配管台帳（PipeInfo） | 80〜120 | 材質・口径・布設年・経過年数・埋設深 |
| **入力 合計** | **約 1,000〜1,400** | |
| 出力（WorkOrder JSON） | 500〜800 | 部材3〜5点＋作業手順＋通知文面 |

> ⚠️ この表は**設計からの見積であり実測ではない**。ピッチでは §3 の実測値のみを提示し、本節の数字は使わない。

### 3.2 年間原価の試算

```
年間原価 = 年間起票件数 × 1起票あたり平均原価
```

Phase 2（1,000台）で年間 Level 1〜3 検知が仮に 500件、うち起票が 300件なら:
`300 × (1起票あたり原価)` が年間のLLM原価となる。これを `docs/business-model.md` の年間システム費用 ¥1,460万 と比較すると、**LLM原価はコスト構造上ごく小さい**ことが分かる見込み。→ 「LLMコストが事業性を毀損しない」ことを定量で示せる。

## 4. コスト削減策

実装済み・実装予定の施策と、それぞれが削るコスト。

### 4-1. スキーマをプロンプトに埋め込みパース失敗を潰す 【OR-2 で実装】

`WorkOrder.model_json_schema()` をプロンプトに埋め込んで出力形式を強制する（`docs/issues-summary.md` #12）。

- **削るもの**: パース失敗によるリトライ。1回失敗すると**プロンプト全体を再送**するため、原価がそのまま2倍になる。
- **副次効果**: スキーマとプロンプトが自動同期し、スキーマ変更時のプロンプト修正漏れが起きない。
- **測り方**: パース失敗率（失敗件数 / 総起票件数）をログから算出。

### 4-2. スペクトル128点を送らない 【設計上の判断】

`AnalysisResult.spectrum` は FE-4 の描画用に128点を持つが、**LLMには送らない**。

- **削るもの**: 128点 × 2値（freq/magnitude）で数百〜千トークン規模。入力トークンの数割に相当する。
- **理由**: LLM の判断に必要なのは `severity_level` / `leak_confidence` / `dominant_freq_hz` / `band_energy_ratio` の要約4値であり、生スペクトルは部材選定に寄与しない。
- **ステータス**: **未実装** — BE-5 でプロンプト構築時に `spectrum` を除外する処理を明示的に入れる（`model_dump(exclude={"spectrum"})`）。

### 4-3. 同一アラートの起票結果をキャッシュ 【BE-5 で実装】

同一 `telemetry_id` への2回目以降の起票はキャッシュを返す（`docs/issues-summary.md` #13）。

- **削るもの**: デモ中の再実演・審査員による再クリックでの重複課金。**デモ本番で最も効く施策**。
- **注意**: キャッシュヒット時は `cost_yen = 0`（新規課金なし）として記録し、平均原価の計算からは除外する。

### 4-4. フォールバックによる呼び出し回避 【OR-3 で実装】

`ORCAROUTER_ENABLED=false` で強制フォールバック。

- **削るもの**: 開発中・リハーサル中の全呼び出し。**実装期間中の原価をほぼゼロにできる**。
- **副次効果**: オフラインでのデモリハーサルが可能（PRD NFR-5）。

### 4-5. 配管台帳情報の要約圧縮 【未実装・余力があれば】

`PipeInfo` をJSONそのままでなく1行の自然文へ要約して渡す。

- **削るもの**: 数十トークン程度。**効果は小さいため優先度は低い**。4-1〜4-4 が終わってから検討する。

### 削減策の優先度まとめ

| 施策 | 削減インパクト | 実装コスト | 優先度 |
|---|---|---|---|
| 4-1 スキーマ埋め込み | 大（リトライ = 原価2倍を防ぐ） | 小 | **高** |
| 4-2 スペクトル除外 | 大（入力の数割） | 極小 | **高** |
| 4-3 キャッシュ | 中（デモ本番で効く） | 小 | **高** |
| 4-4 フォールバック強制 | 大（開発期間中） | 小（OR-3に内包） | **高** |
| 4-5 台帳要約 | 小 | 中 | 低 |

## 5. デモでの提示方法

1. 起票モーダルに **「本起票のAPI原価: ¥X.XX」** を常時表示 → 実測していることが一目で伝わる。
2. ピッチで **「1起票あたり◯円。年間起票300件で年◯円。システム費用の◯%」** と、事業性への影響まで接続して語る。
3. 削減策は「やった」ではなく **「◯%削った」** と数字で語る。4-1 はパース失敗率、4-2 は入力トークン数の before/after で示す。

> ⚠️ **未計測の値を語らない。** §3 が埋まっていない状態では「概算」と明示するか、その話題に踏み込まない。
